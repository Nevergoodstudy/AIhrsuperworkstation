**TalentDesk 下一步改进策略与实施清单**

研究日期：2026-11-16。对象：当前仓库工作区；研究与建议不等于功能已经实现或生产环境已经验收。

后续进展（2026-11-17）：工作包 A 的 F1 / F2 / F3 修复与工作包 B 的容器恢复自动化已落地，远端 CI 的实际容器重启、备份和新卷恢复均通过，正式服务器仍待签收。详见 [第一阶段实施记录](phase-one-results-2026-11-17.md) 和 [v1.1.0 发布说明](releases/v1.1.0.md)。下文保留研究当日的发现、验证结果及规划，不能当作当前版本尚未修复问题的清单。

建议把下一阶段定义为：**让一个企业的 HR 与用人经理，可靠地完成“证据筛选—业务测评—独立复核—推进判断—候选人反馈”，并证明比现有人工方式省事。** 保留单企业、单实例的交付方式，先做好这条业务链。

当前最需要投入的不是更多 AI 功能。代码与定向验证已经暴露出测评会话、招聘阶段和 AI 结果写回的一致性问题；这些应先于外部真实候选人试点处理。修好之后，最高价值的产品增量是负责人和待办、独立评审、候选人通知与结果访问恢复。

以下关于竞品的陈述来自官方公开资料，只表示公开产品能力，不是本次对商业产品的实测，不采信其宣传效率数字。目标用户与工作量是规划假设，仍需试点验证。本报告没有声称穷尽全网产品。

**必须先处理的三类一致性问题**

此处 P0 表示本项目试点的阻断优先级，不是通用漏洞评级；F3 的门槛特指启用外部 AI 的路径。

| 编号与优先级 | 复现条件及实际结果 | 最小修复与验收 |
| --- | --- | --- |
| F1 / P0：旧标签页答案写入另一份测评 | 同一浏览器持有两份有效邀请；A 页保留 revision=0，另一页兑换并开始 B；A 再发送答案。由于共享 td_portal Cookie，且保存体没有预期 examId，在相同题号与匹配 revision 条件下，接口返回 200，答案写入 B，A 仍为空 | 所有候选人会话操作同时验证 Cookie 授权的 exam 与页面预期 examId；覆盖读取、开始、保存、提交、事件和退出。不同则明确拒绝，保留当前草稿；不能仅按客户端传入 ID 查询或授权。前端校验响应 id。新增同浏览器双邀请回归，要求 B 数据完全不变 |
| F2 / P0：考试事件覆盖人工招聘决定 | 测评进行中，HR 手动改阶段为“录用”；候选人提交后，阶段变回“待复核”。撤销测评后，候选人还显示“测评中” | 将招聘阶段和测评状态分清；集中定义允许的自动阶段迁移，终态不得被旧考试事件覆盖。关闭候选人流程时明确撤销或保留有效测评的规则。手动和自动迁移均在事务中记录来源、前后状态、时间、操作者和原因。覆盖开始、提交、超时、撤销、过期、重邀及并发修改 |
| F3 / P0（启用外部 AI 的前提）：旧结果仍可写回 | AI 请求等待时，将岗位要求从 Node.js / SQL 改为 Python，并停用发起 HR；响应返回后仍以 200 保存旧要求的分析。只要引用逐字存在，自由 summary 也可被接受 | 记录 jobVersion、简历版本或 hash、model、promptVersion、requestedBy；写回前重新检查输入及账号状态，过期结果标记 superseded 而非覆盖当前结果。岗位要求修改后，旧结果显式标记过期。第一阶段隐藏自由摘要或明确标为需人工核验；后续概述再关联 evidenceIds，且不能把存在引文等同语义已验证。保留关键词与人工路径；未修复时关闭外部 AI |

F1 的威胁范围是“同一浏览器已经兑换了多份有效邀请”的会话混淆，不代表已证明任意未授权用户可以访问任意答卷。应以数据完整性阻断项处理，避免夸大或淡化。

定位：F1 见 server/app.mjs:23、304–340，src/CandidatePortal.jsx:22–29；F2 见 server/app.mjs:41–46、151–155、240–243、319–336；F3 见 server/app.mjs:169–175，server/ai.mjs:3–31。

**实现时应守住的几个设计细节**

数据迁移采用新增字段 / 表、显式版本迁移、事务和迁移前快照；在旧库副本验证后上线。历史阶段时间不可凭当前 updated_at 伪造，应标注“历史未知”并从迁移后准确采集。历史 reviews 迁为已提交记录时保留原时间与作者；没有 assignments 的旧考试沿用明确的 legacy 发布策略，不能让历史记录意外永久锁死。

招聘阶段是业务决定，测评状态是活动状态。先约定迁移矩阵，再集中实现 applyTransition 一类小 Interface，内部处理授权、乐观锁、事件与副作用。自动事件只在预期旧状态满足时推进，不能覆盖终态；特殊回退由 HR 显式确认并记录原因。撤销 / 过期后回到哪一步由真实岗位流程决定，而不是随意写死回退。

review_assignments 至少需要 exam_id、reviewer_id、required、due_at；任务状态优先从复核记录导出，避免多份完成状态互相漂移。普通评审人提交前只拿到自己的内容与他人完成状态；任何 HR 特殊查看权限须明确配置并留审计。1–5 分应有可观察的分档锚点，显示分布和分歧；不要把简单平均换算的 80 / 100 宣传为标准化能力测量。

分页先采用稳定排序的 created_at + id 游标和有上限的 limit；过滤、权限约束与统计口径放到服务端。索引按实际查询和 EXPLAIN 结果添加。数据库继续用 SQLite 单实例，不因“将来可能扩展”先引入 Redis、Kafka、微服务或 PostgreSQL。只有实测锁等待、写入竞争、容量、备份窗口或多实例要求超出边界时，再评估迁移。

部门字符串的精确匹配当前是既定授权规则。第一阶段冻结随意改名并做统一选择；出现部门改名、多部门或岗位级授权需求时，再迁移 department_id 与岗位成员关系。迁移必须对照权限矩阵，不能把新增 owner 当成唯一授权依据而造成越权或意外失权。

简历导入的第二步应是“解析预览—校正联系方式 / 正文—确认保存”，保留原件、解析版本和修正记录；正文修正使旧 AI 结果过期。OCR 在样本证明扫描件确实阻断业务后再上，先保留粘贴正文和人工校正。重复提示只面向有权查看相关资料的 HR；同一人在不同岗位应允许独立申请，不能用全局邮箱唯一约束粗暴拦截。

当前邀请原 token 只存摘要，不能通过数据库重新找回原链接。结果访问恢复应发行新的、仅可读结果的短期 token 并可撤销，不把它复用为测评作答凭证。若后续引入邮件 outbox，需要明确敏感链接的短期加密存储与清理；不能为了可重试而长期明文存 token。SMTP accepted 仅代表发送服务接受，超时重试也不能承诺 exactly-once。早期先提供 HR 人工通知及确认，避免过早建设完整消息平台。

源码还显示初次发信与重发的限流不一致，且缺少 sending / unknown 等状态；这是已确认的设计缺口，本轮未复现真实重复投递。E 先保证按钮防并发、两个入口共用限流并准确显示接受 / 失败 / 结果不明；结果不明时由 HR 核查，不盲目自动重试。若试点必须实现跨进程可靠重试及完整发送账本，需另加 1–2 开发人日并顺延其他非阻断范围，不把它隐藏在原预算内。

server/app.mjs 已集中较多业务。按正在修改的流程提取 portal、pipeline、reviews、analysis 等深 Module，把校验、授权和事务封装在清楚的 Interface 后，通过真实路由测试 Seam；保留现有 Express 和 SQLite。不以一次性重构全仓、全面改 TypeScript 或引入多层空抽象作为开工前提。前端也按候选人、答卷、待办逐步拆分，先处理被改到的长行与状态逻辑。

**试点怎么证明值得继续**

建议先验证 1 个企业、1–2 个岗位、2 名 HR / 管理员、2–3 名用人经理、20–30 名已授权候选人的流程。岗位、人员与数量是试点设计假设，不是现有用户规模。试点前访谈 HR、经理各 2–3 人，候选人或自愿模拟人员 5 人，并现场观察操作，不只征集功能清单。

- HR：复盘最近一次招聘资料流转，谁需要被催、催几次、哪些内容重复录入；现场找到“现在应该由谁处理”的答卷。
- 用人经理：不看覆盖率及他人评价时，哪些原文 / 答案足以支持推进；两人评分差异大时，如何形成最终理由。
- 候选人：能否准确说出岗位、时长、保存成功标志、AI 规则、求助方式和反馈时间；丢失链接后能否回到原反馈。

下表都是建议目标，当前基线未知。第一周先记基线，再与同岗位、相近材料复杂度的后续样本比较，记录样本量及退出原因；小样本只能验证早期可用性。

| 指标与定义 | 建议试点目标 / 判定方法 |
| --- | --- |
| 错写 / 丢失已确认保存答案 | 所有异常演练和真实试点均为 0；发生一次先停止扩量并排查 |
| 下一步责任完整率：待处理记录中有责任人、行动、期限的比例 | 100%，不能只填一个没有接到任务的人名 |
| 复核按时率：已到应完成时间的必要评审任务中，在期限内提交的比例 | 首先约定期限，例如两个工作日；目标 ≥90%，同时披露逾期与改期数量 |
| 人工催办量：每份答卷从提交到形成推进建议的额外催办次数 | 较基线下降 ≥50%；不将自动消息数直接等同节省时间 |
| 材料处理耗时：HR / 经理每份材料的实际操作时间中位数 | 目标下降 ≥25%；同时检查证据质量没有下降 |
| 候选人提交率：已开始考试且观察窗口已结束的人中成功提交比例 | 目标 ≥90%；同时报告邀请到开始比例、撤销、退出与技术求助原因 |
| 反馈可达性：反馈发布后约定窗口内确认收到通知并能打开结果的比例 | 目标 ≥90%；SMTP accepted 不计作本人确认送达 |
| 决定可解释性：抽样推进 / 不推进记录中能指向具体岗位要求与答题证据的比例 | 目标 ≥80%；覆盖率本身不是理由，未找到证据不等于不具备能力 |
| 评分校准：至少 10 份答卷独立双评，逐题相差 ≤1 分的比例 | 目标 ≥80%；大分歧全部讨论并留理由，不据此宣称测评有效性已获统计证明 |

技术预算也应先测后承诺：在记录配置的目标服务器、1,000 份合成候选资料和 20 个活跃作答会话下，建议先以普通列表 P95 ≤800ms、自动保存 P95 ≤1s、5xx <1% 作为测试起点，排除模型 / SMTP 外部耗时并单独报告；不代表当前系统已达到，也不直接换算成生产容量。任何冲突误覆盖均不能靠平均延迟掩盖。

恢复目标先由业务签收。可用试点讨论值为 RPO ≤24 小时、RTO ≤2 小时；若业务不能接受一天数据损失，应提高备份频率并重新演练，不能仅修改文档数字。删除请求、备份留存和恢复后重新应用删除 / 停用 / 撤销操作，均需明确负责人和记录。

继续投入的条件：业务负责人和经理实际使用；关键流程稳定；催办或处理时间有可观察改善且评价依据没有变差。若没有改善，先收缩到“测评与人工复核”单一场景，修流程与题目，不以再堆 AI、渠道或看板解释失败。
