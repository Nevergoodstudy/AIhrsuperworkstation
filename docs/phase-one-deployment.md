记录日期：2026-11-17。当前开发机未安装 Docker CLI，因此本机没有执行容器启动、容器重启或新卷恢复验收。以下脚本已加入 CI，但只有实际运行成功后的报告才能作为容器验收证据。代码与本地验证结果见 [第一阶段实施记录](phase-one-results-2026-11-17.md)；服务器正式签收仍按 [运维手册](operations.md) 和 [验收记录](acceptance.md) 执行。

## 自动化验收

在装有 Docker Engine、可访问 Docker daemon 和 Node.js 24 的隔离环境中，从项目根目录执行：

```sh
docker build -t talentdesk:ci .
node scripts/container-smoke.mjs talentdesk:ci > container-smoke-report.json
```

CI 现在在镜像构建后运行同一个脚本，任何业务断言、容器错误或资源清理失败都会使任务失败，并上传 JSON 报告。报告记录实际镜像 ID、开始时间、耗时和已通过的检查。脚本用唯一的 `talentdesk-smoke-…` 名称和标签创建独立容器及三个临时卷，结束时按确切名称及标签清理；不读取 `.env`，不挂载现有数据卷，不删除其他容器或卷。

脚本执行以下验收：

1. 使用镜像默认非 root 用户、只读根文件系统、`tmpfs`、删除 capabilities 和 `no-new-privileges` 启动应用，检查实际 UID、数据目录 700 和数据库 600 权限。
2. 将端口仅发布到主机 `127.0.0.1` 的随机端口，检查 `/api/health` 和 `/api/ready`，通过真实 HTTP 登录并创建合成岗位、题目、测评、带原件候选人、邀请、开始及保存答案。
3. 重启容器，验证答案、原件和员工及候选人会话仍可读取。
4. 用无网络备份容器、只读源卷运行现有 `createBackup` / `verifyBackup`，同时校验 SQLite、清单和原件。备份之后修改合成候选人，检验恢复时能回到快照版本。
5. 在全新独立卷的全新子目录恢复；确认拒绝覆盖已有目标目录，原件字节一致，员工和候选人会话表已清空。
6. 从恢复卷启动第二个应用容器。旧 Cookie 必须失效；重新登录及兑换原邀请后，恢复的候选人、原件和答案可读。

所有资料均为合成数据，SMTP 和外部 AI 配置为空。候选人请求携带 `X-Exam-Id`，仍同时使用授权 Cookie。

## 自动化未覆盖的正式签收

此脚本直接通过主机回环 HTTP 访问应用，使用手动 Cookie 客户端。它不启动 Caddy、不验证浏览器对 Secure Cookie 的真实行为，也不代替真实域名 HTTPS、受信代理、企业 SMTP、异地备份或生产回滚演练。

| 项目 | 取得可签收证据的方法 | 当前状态 |
| --- | --- | --- |
| 镜像启动、重启、备份和新卷恢复 | 在 Docker 环境运行脚本，保存成功报告及 CI 运行链接 | 自动化已提供；当前开发机未执行 |
| 真实 HTTPS、Secure Cookie、外网作答 | 隔离服务器运行完整 Compose / Caddy，用外网浏览器完成邀请到反馈链路 | 待服务器验收 |
| SMTP 接受及真实收件 | 使用企业测试邮箱发送，检查收件箱及退信记录 | 待企业测试配置 |
| 外部 AI | 经授权的合成资料及企业允许的服务配置，检查来源和失败行为 | 待企业测试配置 |
| 异地恢复及实际 RPO / RTO | 从独立存储取回备份，恢复至新卷，记录快照时间、恢复耗时及数据损失窗口 | 待运维演练 |
| 删除、停用、撤销的重新应用 | 恢复旧快照后对照快照之后的操作清单，开放入口前重做必要操作 | 必须由运维及业务负责人签收 |
| 回滚 | 保留旧镜像 ID 和旧卷，使用与旧数据库兼容的代码及快照恢复并检查业务 | 待隔离服务器演练 |

恢复会清空会话，但不会自动撤销快照中的邀请，也不能追回快照之后的删除、停用、改密或撤销。这些操作在正式恢复后需要按运维手册重新应用。脚本清理容器和临时卷不构成生产数据处置操作。
